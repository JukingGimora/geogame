# 系统架构设计
> 2026-07-09 · V1 —— 目标：H5验证起步，同一底座长出小程序、独立App、国际版

## 0. 三条铁律（所有设计决定的出发点）

1. **后端与数据是永久资产，前端是可更换的壳。** API 一旦定型，换壳（H5→小程序→App→国际版）不改后端一行。
2. **所有"国内耦合"的东西都藏在接口后面。** 地图、逆地理编码、对象存储、登录方式、备案——每一样都是可替换的 Provider，国际版 = 换一组 Provider 配置 + 海外部署一套实例。
3. **必须正确的逻辑不经过AI模型**（幻觉隔离，见立项报告第四节）。

│(主数据)│(队列/缓存/│ 直传图床) │(admin路由) │

**AI挂了游戏照玩**：AI结果异步写回，客户端轮询/推送拿到就展示，拿不到就只出人类结算。

## 2. 前端

**框架：uni-app + Vue 3 + TypeScript，从V0第一行代码开始就用它。**
- 理由：一套代码编译 H5 / 微信小程序 / iOS / Android。V0 只发 H5，V1 编译小程序（改动集中在登录和支付适配），V3 出 App——三次"换壳"共用同一套页面和逻辑，这就是"打好底座"在前端的含义。
- 备选方案是 Taro(React)；不选原生开发（V0 阶段成本不合理）。将来若 App 要极致体验，届时用收入养原生重写，API 不动。

**地图适配层（关键抽象）**：定义 `MapAdapter` 接口（打点、取点、飞线动画、迷雾图层）。

**V0 决定（2026-07-09）：不接任何外部地图API。** 用自绘地图——中国省市边界 GeoJSON（阿里 DataV GeoAtlas 免费公开数据）+ canvas 自绘，风格化手绘感、支持缩放到市级取点精度。理由：零API费用、零key、美术上与迷雾+像素气质一致（真实地图反而破坏游戏感）、三端（H5/小程序canvas/App）同一套渲染代码。判分只需要点击处经纬度，自绘地图完全满足。

后备实现（仅在将来确有需要时启用，均非按次计费的商业API）：小程序原生 `<map>` 组件、国际版 MapLibre GL + 开源瓦片（OSM/Protomaps）。

**坐标铁律：与后端交换永远是 WGS-84**，GCJ-02 转换只发生在 MapAdapter 内部边界上（wgs84↔gcj02 纯算法函数，前后端各留一份）。

**迷雾地图**：不依赖地图供应商——canvas 叠加层画迷雾/点亮/照片钉，三端通用，这层是自己的核心资产。

**i18n**：所有界面文案从 V0 起就走 locale 文件（`zh-CN.ts` 起步），代码里不出现硬编码中文。这是国际版成本几乎为零的前提，事后补做是全量返工。

## 3. 后端（FastAPI）

**分层**：沿用 liangnongtec 验证过的 `api → services → repositories → models`，但两处升级：
- **数据库 PostgreSQL**（不用SQLite：并发写、以后要地理查询和全文检索）+ SQLAlchemy 2.0 async
- **注意路由顺序**：静态路由先于参数路由注册（liangnongtec 的教训）

**API 约定**：
- `/api/v1/...`，纯 JSON，OpenAPI 自动文档
- 版本号在路径里，将来 v2 并行不破坏老客户端（App 用户不升级是常态，这是"底座"级决定）
- 后端只返回错误码和数据，不返回面向用户的句子（文案是前端 locale 的事——国际化铁律）
- 时间一律 UTC 存储、ISO8601 带时区输出，客户端按本地时区渲染（liangnongtec 时区之痛的根治版）

**认证（为三端+国际版设计）**：
- `users` 表与 `auth_identities` 表分离：一个用户可挂多个身份（provider: `guest` / `wechat` / `phone` / `apple` / `google` / `email`，唯一键 provider+provider_uid）
- **V0 用游客账号**：首次打开静默创建 guest 身份（设备生成密钥），先玩起来零门槛；后续"绑定手机/微信"只是给同一个 user 挂新身份——**种子用户的资产从第一次打开就在正式 User 表里，永不迁移**
- JWT access(短) + refresh(长)，跨端通用；小程序登录 = wx.login code 换 identity，App 国际版 = Apple/Google 登录，同一套表结构

**图片链路（带宽不碰自己服务器）**：
1. 客户端请求 `/api/v1/photos/upload-ticket` → 后端返回 OSS 签名直传 URL
2. 客户端直传 OSS（原图+缩略图）
3. 回调/确认接口落库 `photos`（status=pending），进审核队列
- `StorageProvider` 接口：V0 实现阿里 OSS，国际版换 S3/R2，业务代码不动
- 上传时读 EXIF 坐标（无则手动标点），**入库即抹除原图 EXIF**（隐私）

**地理**：
- 照片坐标存 WGS-84（`lat/lng` double 起步，量大再上 PostGIS）
- 判分 = Haversine 距离 + GeoGuessr 指数衰减曲线，纯函数，含单元测试
- 区域归属：V0 用本地省级质心最近邻（零外部调用，已实现于 `geo.py`）；将来若需市级精度，用本地 GeoJSON 边界做点面判断（依然零API），逆地理编码 Provider 仅作最后备选
- `regions` 树：`id / parent_id / level / name_i18n(jsonb) / bounds`，无限深，materialized path 查祖先链。中国和国外是同一棵树上的枝

## 4. 数据模型（核心表）

| 表 | 要点 |
|---|---|
| `users` | 昵称、段位、创建时间。资产之根 |
| `auth_identities` | provider + provider_uid → user_id，多对一 |
| `photos` | uploader、OSS key、WGS-84坐标、region_id、story、难度、status(pending/live/rejected)、语言标签 |
| `regions` | 树（见上），章节/关卡挂在 region 上 |
| `runs` | 一轮（5关），user + 章节 + 状态 |
| `rounds` | 一关：run_id、photo_id、玩家落点、距离、得分、用了哪些提示 |
| `ai_guesses` | photo_id、模型落点、距离、推理全文、模型版本——**既是玩法数据也是未来微调语料** |
| `hints` | photo_id + 级别(1-4) + 内容 + 来源(uploader/ai/system)；③④由程序从坐标生成 |
| `points_ledger` | **只追加的积分流水**（user、类型、数额、关联对象）。余额=SUM，可审计可反作弊回溯，防刷的地基 |
| `comments` / `reactions` | 留言、"我也去过"、猜中通知的数据源 |
| `reports` / `moderation_log` | 举报与审核记录（先审后发的法定留痕） |
| `daily_quota` | 每日轮次限额与激励视频加次 |

**防刷在数据层就位**：同设备/同IP对自己照片的 round 不入 ledger；单照片积分封顶用 ledger 聚合校验。

## 5. AI 子系统

- **vLLM 常驻服务**跑 Qwen2.5-VL-7B AWQ 量化（显存约 8-10G / 24G），OpenAI 兼容接口，只监听 localhost
- **arq worker** 消费 Redis 队列：`ai_guess(photo_id)`（照片上线时预算好，不在玩家等待路径上）、`gen_hint(photo_id)`（提示②草稿，审核时人扫一眼）
- 输出结构化 JSON（落点坐标+置信度+推理文本），解析失败自动重试一次后标记 ai_unavailable
- **幻觉隔离在架构上的体现**：判分服务、提示③④生成器、复盘事实层（车牌前缀表/行政区划表查询）都在主应用内，是普通代码；AI worker 只产出"对手的猜测"和"标注为推测的线索"，其结果表(`ai_guesses`)与判分路径物理分离

## 6. 审核后台

- 同一个 FastAPI 下的 `/admin` 路由组 + 独立简易页面（这里可以用你熟的 Alpine.js 单文件，内部工具不讲究）
- 队列视图：待审列表 → 大图 + 故事 + 坐标地图 + AI预审分（后期）→ 通过/拒绝(理由模板)/打码后通过
- 权限：admin 角色 JWT，仅白名单账号

## 7. 部署与运维（4090D 单机）

```
docker-compose：
  caddy      # 443 TLS 自动证书，反代
  api        # uvicorn × 2
  worker     # arq
  vllm       # --gpus all
  postgres   # 挂本地卷
  redis
```
- **域名 + ICP备案是前置事项，现在就启动**（小程序 request 合法域名必须已备案，流程要几周，是路径上最慢的一步）
- 备份：每夜 pg_dump 加密传 OSS；照片本体天然在 OSS
- 国际版部署 = 同一套 compose 在海外 VPS 再起一份（GPU 可先用 API 或小卡），数据独立（数据出境合规反而更干净），`regions` 树各自挂枝
